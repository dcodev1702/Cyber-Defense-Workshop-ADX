# Changelog

## Unreleased

### 2026-07-26 — closed the lexer gap the tests had been documenting (H1c)

- Taught the gateway's statement lexer about backslash escapes and `@`-verbatim literals, closing a bypass that let a crafted string hide a second statement. Given `print x = "\""; .drop table T`, Kusto reads the literal as a single `"` followed by a second statement, while a lexer that models only `''`/`""` doubling sees the quote close and immediately re-open — swallowing the `;` and the `.drop` into what it believes is one `print` statement, which then passed validation. Non-verbatim literals now honour `\` as an escape, `@"..."` and `@'...'` (including the `h@'...'` obfuscated form) treat a backslash as data, and a doubled quote inside a verbatim literal stays inside it.
- Made an unterminated literal or comment a refusal rather than a guess. If the lexer cannot tell where a statement ends, neither can the policy, so the request is rejected instead of forwarded on an assumption. Over-splitting was already the safe direction — an unexpected extra statement is refused — and this keeps every remaining ambiguity on that side.
- The existing test for this had been asserting the *vulnerable* behaviour. `rejects a statement hidden inside a string from reaching Kusto` asserted `allowed: true` for the smuggling payload, with a comment explaining that only the raw-text deny scan caught the subset of payloads containing a denied primitive — so `.drop table T`, which contains none, got through. The test now asserts the statement is seen and refused on its own merits. A test that documents a gap is worth having; one that outlives the gap is worth updating.
- Seven new tests cover the reported payload in both quote styles, verbatim backslash handling, doubled quotes, the `h@'...'` form, all four unterminated cases, and that ordinary multi-statement splitting still works. Suite is 63 tests.

### 2026-07-26 — unpinned the emulator, deliberately

- Reversed the digest pin added earlier the same day. This instance runs indefinitely rather than for a single event, so it tracks the current emulator and picks up Microsoft's fixes as they ship, rather than freezing on a build that will age. Recorded as a decision, with the trade stated in `compose.yaml` rather than left for someone to rediscover: Kustainer writes its persistent database in the format of the build that created it, and a different build cannot attach it, so when the image moves the snapshot in `data/local-kusto` does not come with it. That is recoverable and rehearsed — the NDJSON payload is what actually restores, via `Import-GeneratedDataToKustainer.ps1`. `KUSTO_IMAGE` still accepts a full reference, so pinning for a specific delivery remains one environment variable away.
- Removing the pin also removed the recreate it introduced. Confirmed with `--dry-run`: `docker compose up -d` now reports the `kusto` container as `Running` rather than `Recreate`, because the resolved image string matches what the container was created with again. The persistent database registration is no longer one `up` away from being destroyed.
- Changed the emulator build from an assertion to an observation in `Test-WorkshopReadiness.ps1`. Asserting a fixed build would have turned every legitimate Microsoft update into a red preflight, which trains people to ignore preflights. The build and product version are now reported, and the gate is the table and row count — which is the check that actually catches a version move, since the symptom is a database that will not attach. The remedy on that check now names the import as the fix for that case too, so the failure is explainable rather than mysterious.

### 2026-07-26 — closed the path around the gateway, and proved it closed

- Added [`scripts/Set-WorkshopNetworkIsolation.ps1`](scripts/Set-WorkshopNetworkIsolation.ps1), which stops the Cloudflare connector reaching Kustainer directly. The `edge`/`backend` split stops `kusto` resolving for the connector, but not an ingress rule naming the backend IP. The rule is one `DOCKER-USER` entry — the chain Docker evaluates before its own accept rules and never rewrites — dropping packets that arrive on the edge bridge and leave on the backend bridge. Applying it changed nothing for the class: verified over the live tunnel afterwards at 79 tables and 623,832 rows, with the ADX web UI handshake and the scenario queries unaffected.
- Corrected the diagnosis recorded earlier the same day. The first explanation blamed `DOCKER-FORWARD` accepting traffic from every bridge. That was wrong, and testing two freshly created networks disproved it — they could not reach each other at all. Docker **does** isolate bridges (`! -i br-X -o br-X -j DROP` in the `DOCKER` chain). What defeats it is **publishing a port**, which inserts an accept above those drops:
  `-A DOCKER -d <kusto-ip> ! -i br-<backend> -o br-<backend> -p tcp --dport 8080 -j ACCEPT`.
  That accept is not restricted by source network, so every container on every other bridge could reach the engine. Binding the host side to `127.0.0.1` constrains the host, not other containers. The mitigation is unchanged; the reason it was needed is now stated accurately in `compose.yaml`, the infra README, and the IaC guide.
- Made the rule survive the topology changing under it. Docker names a bridge after the network ID, so any `docker compose down` yields new bridge names and leaves the old rule pointing at a dead interface — still present in `iptables -S`, protecting nothing. The script reads the edge and backend networks from the running containers instead of hard-coded names, derives bridges from live network IDs, and clears rules of its own shape whose interfaces no longer exist before applying the current pair. It refuses to act if the two networks resolve to the same bridge, and refuses if the connector and the emulator share a network, where no firewall rule could help.
- Added [`scripts/Test-WorkshopNetworkIsolation.ps1`](scripts/Test-WorkshopNetworkIsolation.ps1), which sends packets rather than reading firewall rules, because a stale rule reads as correct. It asserts Kustainer is unreachable from the edge network by name and by raw IP, still reachable from the backend network so the gateway works, that the gateway is still reachable from the edge network so students get in, and that `127.0.0.1:8080` still answers so the instructor and the import scripts are unaffected. Run against the unprotected stack it failed on exactly one assertion — the raw-IP bypass — and passed the other five, which is the behaviour that makes it worth trusting.
- Gave the test a `-SelfTest` mode and put it in CI (`.github/workflows/network-isolation.yml`). It builds two throwaway networks and a listener that publishes a port, then asserts reachable, blocked after applying, still reachable from its own network, and reachable again after `-Remove`. It needs no workshop stack, and the job fails if any rule is left behind. Writing it caught two defects in the test itself before it caught anything else: a `nc -l` listener that served one connection and left gaps reading as "blocked", and a listener with no published port, which was already isolated and so proved nothing.
- Wired both into `Start-CloudflareAdxTunnel.ps1 -Apply`, which now applies the rule and runs the boundary test after the connector starts, failing the run if the connector can still reach Kustainer directly. `-SkipNetworkIsolation` opts out. This is the right place because the rule must be reapplied whenever the networks are recreated, and this script is what brings the class route up. Terraform cannot own it: it is host firewall state inside the Docker VM, not a Cloudflare or Compose resource.

### 2026-07-26 — the network split does less than it claimed

- Corrected a security claim the repository could not support. `compose.yaml` and the entry below stated that splitting `edge` from `backend` meant `cloudflared` "cannot reach `kusto:8080` no matter what the dashboard-managed ingress rule is set to", making the bypass "architecturally impossible". Tested from a container attached to `edge` only — the same network position as the connector — the result was: `kusto` does **not** resolve, `kusto:8080` by name is blocked, but `172.19.0.2:8080` by raw IP is reachable and `GET /v1/rest/ping` against the engine answered. The separation blocks the realistic misconfiguration (a hostname in an ingress rule), not a deliberate one (an IP).
- The cause is a Docker change, not a Compose mistake. On Docker 29.6.2 the old `DOCKER-ISOLATION-STAGE-1`/`-2` chains are gone. *(Corrected later the same day: the mechanism named here — `DOCKER-FORWARD` accepting every bridge — was wrong. Docker does isolate bridges; publishing a port inserts an accept above that isolation. See the entry above.)* Only `internal: true` produces a drop, which was confirmed on a throwaway network — and confirmed to also disable published host ports, so it cannot be applied to `backend` without taking away the `127.0.0.1:8080` the instructor and `Import-GeneratedDataToKustainer.ps1` both depend on. A `DOCKER-USER` rule pinned to the two bridge interfaces is therefore the mitigation, and it is host state rather than repository state.
- What actually enforces the boundary is therefore the read-only gateway plus the Cloudflare ingress configuration and Access policy, not the network topology on its own. *(Now backed by `Set-WorkshopNetworkIsolation.ps1`; see the entry above.)* A control that is documented accurately is worth more than one that is documented confidently.

### 2026-07-26 — the hardened gateway locked out the client it exists to serve

- Fixed the database allowlist rejecting the Azure Data Explorer web UI's opening calls, which made the workshop unreachable from `https://dataexplorer.azure.com` entirely. **Add connection** reported only `Request failed with status code 403`. The allowlist required every request to name a permitted database, but the web UI's first management calls deliberately carry no database — discovering which databases exist is what they are for. Every database-scoped call worked, so the failure appeared only at the one step every student must complete first. A request naming no database is now permitted for cluster-scoped discovery (`.show version`, `.show databases`, `.show databases schema`, `.show schema`) and only on the management endpoint; a database-less *query* would run against the engine's default database, which is what the allowlist exists to prevent, and is still refused.
- Forwarded `/v1/rest/auth/metadata` instead of answering `404`. The web UI fetches it before it will talk to a cluster at all; it is how the browser learns the local emulator wants no Entra sign-in. Kustainer answers `200` with a body carrying no data, so there was nothing to withhold.
- The gap was in the testing, not the reasoning. The gateway's own suite and every probe run against it supplied an explicit database, so the database-less path — the one path the real client always takes — was never exercised. Three tests now cover it: the full handshake succeeds, the auth-metadata probe is forwarded and rejects non-GET, and a database-less request is still refused for row data, for non-discovery management commands, and for a whitespace-only database name. Suite is 55 tests.
- Diagnosed from the gateway's own structured audit log, which recorded `{"outcome":"blocked-database","db":null,"status":403}` against the browser's requests. That log was added in the hardening pass for exactly this purpose and paid for itself the first time it was needed.

### 2026-07-26 — the hardened gateway was not the gateway that was running

- Documented that the read-only gateway must be rebuilt explicitly, because a stale build had been serving the class. The gateway is a Compose `build:` service, so `docker compose up --detach` reuses whatever image was last built on the host and never consults the source. After the gateway hardening landed, bringing the stack up on the new Compose definition left a container running an image built five days earlier, from before the hardening commit: `.show queries` — the disclosure command the allowlist exists to stop, and the one named in the allowlist's own comment — was answered `200`. The source was correct, the tests were green, and the policy was not in force.
- The verification that should have caught this reported success instead. `docker compose ps` said `healthy` and the container health check passed, because the health check only proves the process answers on `/healthz`; neither can distinguish a current policy build from a stale one. Two of the three denials observed against the stale image were also not the gateway's doing — they carried Kusto's `400`, not the gateway's `403` — so a check that only recorded status codes read as enforcement where there was none. Refusals are now attributed to their source before they are counted as evidence.
- The instructor checklist step that read "confirm `kusto-readonly-gateway` is healthy" now rebuilds it first with `docker compose up --detach --build kusto-readonly-gateway` and confirms the policy itself: `.show tables` must succeed and `.show queries` must return `403`. The same warning is in the README's gateway section. Rebuilding the gateway alone does not disturb the `kusto` container or the persistent Student snapshot.
- Verified after the rebuild: all 52 gateway tests pass on the Node version the container actually ships, and every one of ten allow/deny cases behaves correctly with each refusal attributed to the gateway rather than to Kusto.

### 2026-07-26 — repository evaluation follow-up

Work from the "Suggested order of work" in `REPO-EVALUATION-2026-07-26.md`, taken in value-per-effort order. Every change below was verified where a runner exists: the gateway suite runs green (52 tests), all PowerShell files parse cleanly and lint with zero error-severity findings, `Test-WorkshopPackage.ps1` passes on a clean clone, `Test-RepositorySafety.ps1` was exercised against a fixture repo, and `compose.yaml` and every workflow validate.

Gateway (`tools/kusto-readonly-gateway/server.mjs`):

- Stopped one HTTP request from killing the class gateway. A request body of the four bytes `null` parsed successfully and then dereferenced `null.csl` inside an `async` handler with no `catch`, which Node turns into a process-ending unhandled rejection — under `restart: unless-stopped` a single repeated `curl` became a restart loop, and every student has a terminal open. The handler body is now wrapped so every failure path answers with a status instead of crashing, non-object JSON bodies (`null`, `true`, `42`) are rejected with `400`, and `process.on('unhandledRejection')` and `process.on('uncaughtException')` are installed as a second layer. This was the single highest-value change in the repository.
- Closed the validate-one-thing, forward-another bypass. The gateway validated the `csl` it parsed with V8 but then forwarded the client's raw bytes, so any parser disagreement between V8 and Kustainer's .NET deserializer — duplicate keys, key casing, escaped key names — let a body like `{"csl":".show tables","Csl":".drop table X"}` read as harmless in the gateway and execute as the drop downstream. The forwarded body is now rebuilt from the validated fields (`csl`, `db`, an allowlisted subset of `properties.Options`) so the gateway forwards exactly what it checked.
- Forced read-only request options server-side. `properties` was forwarded untouched, so a student could set `notruncation: true` and an unbounded `servertimeout`. The rebuild drops every `Options` key that is not allowlisted, clamps `servertimeout` to `KUSTO_MAX_SERVER_TIMEOUT_SECONDS` (default 240), forces `query_language = 'kql'`, and — unless `KUSTO_FORCE_READONLY=false` — sets `request_readonly = true`. The escape hatch exists because Kustainer builds vary in whether they honour that option; it defaults on.
- Rejected the query-language egress and code-execution primitives that never start with a dot. "Does not start with `.`" is not the same as read-only: `externaldata`, `evaluate python/R`, the `http_request`/`sql_request` family, and `cluster(...)` all reach outside the database. They are now denied on the raw request text, so a primitive hidden inside a string literal is rejected too — over-blocking there fails closed, which is the correct direction for a policy boundary.
- Replaced the blanket `.show` allow with a metadata-read allowlist. `.show` is read-only for data but not for secrets: `.show queries` and `.show commands-and-queries` echo other students' query text, `.show journal` is the full command history, and on the managed ADX path `.show ... principals` discloses real tenant identities. Only `.show version`, `.show schema`, `.show databases`, `.show databases schema`, `.show tables`, `.show table <t> schema`/`cslschema`, and `.show functions`/`.show function <f>` are permitted.
- Added a database allowlist. `payload.db` was never inspected, so a student could target `$systemdb` or `KustoMonitoringPersistentDatabase`. `KUSTO_ALLOWED_DATABASES` (set to `CyberDefendStudentSnapshot` in Compose) is now checked before forwarding; unset means no restriction.
- Added rate limiting and a concurrency cap. Nothing bounded requests or query cost, so one `range i from 1 to 10000000000 | ...` could wedge the shared 4-CPU Kustainer for the whole room. Each source address now gets a token bucket (`KUSTO_RATE_BURST`, `KUSTO_RATE_PER_MINUTE`) and in-flight upstream queries are capped (`KUSTO_MAX_IN_FLIGHT`, default 8); over-budget clients get `429` with `Retry-After`.
- Added a structured audit log. The gateway now emits one JSON line per decision (`forwarded`, `blocked-kql`, `blocked-database`, `rate-limited`, `at-capacity`, `unknown-route`, `handler-error`), so a class incident is answerable from `docker compose logs` instead of guesswork — and in a cyber-defense workshop that log is itself a teaching artifact.
- Fixed the oversized-body path so the client actually receives the `413`. The body reader destroyed the socket, which raced the response into a connection reset; it now pauses the request, writes the `413`, and closes the connection after the reply is flushed.

Gateway tests and container:

- Expanded `server.test.mjs` from 9 tests to 52, covering the null-body crash, the canonical-forwarding rebuild, the `.show` allowlist (allowed and disclosure commands), the egress-primitive denials, the database allowlist, the rate limiter and in-flight cap, and the `403`/`404`/`405`/`413` error paths that were entirely untested. `npm test` runs green.

Added `.dockerignore` and a `package-lock.json` so the build context is minimal and `npm ci` is possible.

- Added `scripts/Restore-LocalKustoSnapshot.ps1`, so restoring is a repeatable operation rather than something reconstructed by hand under pressure. Verified against the current archive: 79 of 79 tables and 623,832 of 623,832 rows, table-for-table identical to the live cluster, with the workshop's credential access queries returning the expected results.
- Recorded why the NDJSON payload is what makes an archive restorable. The emulator registers a persistent database inside the container rather than in the mounted state directory, so a fresh container cannot attach persisted state another container wrote; `.create database ... persist` fails with an internal service error and `.attach database` reports a missing V11 pointer.
